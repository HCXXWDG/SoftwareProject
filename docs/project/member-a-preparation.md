### 新旧接口必须分清

现有路线响应尚无 comparisonId、来源和评分状态字段；现有通勤请求仍传客户端评分与分钟数。comparisonId、operationId 等名称在启动书中是建议设计，须经 S00 确认后才能写成正式契约，不能假设服务器已经支持。

现有入口包括 POST /api/v1/routes/compare、POST /api/v1/reports、POST /api/v1/commutes/complete、GET /api/v1/commutes/trends，以及 GET /api/v1/routes/history?limit=10。历史后端入口已存在，前端尚需增加服务方法和类型。路径与最终字段以联调时后端实现为准。

### 必须形成书面约定的六件事

1. 网络、超时、取消、HTTP 服务错误、业务错误和格式错误如何区分；错误码及可重试含义由谁定义。
2. 底图模式、后端可用性、路线来源、反馈来源和评分状态如何组合；哪些组合允许反馈与完成通勤。
3. 比较快照何时保存、何时过期、属于哪个设备；demo 重启后如何提示重新规划。
4. 同一次通勤操作 ID 何时创建、失败时如何复用、刷新后如何恢复；同 ID 不同内容如何报冲突。
5. 反馈新增、重复、限频和失败如何返回；成功写入与后续热力刷新失败如何分别通知 C。
6. 趋势时区、空日期、历史旧字段、新标签和预计秒数如何解释，缺失数据不得填零冒充有效值。

能力设计采用同一原则：离线底图不自动等于后端离线；演示路线不能进入真实通勤统计；允许操作与禁用原因应一起传给展示组件。样例覆盖真实有效、数据不足、演示、无路线、单路线和服务失败。

## 四 请求与路线任务执行单

### A01 统一请求与错误处理 8工时

目标是让任何请求都能结束加载，并给出可判断、可恢复的结果。先在 services/api.ts 建立统一错误表示和超时策略，再为 route、heatmap、commute 等服务逐项接入，不在页面重复拼接错误判断。

实现时合并超时与调用方取消信号，清理定时器和监听；主动取消不弹失败提示。对关键响应验证必要字段、数组与数值，而非仅使用 as T。设备标识读写失败时采用受控会话回退，说明刷新可能丢失归属的限制。写入请求不自动重试。

验收场景：永不返回的请求超时退出加载；HTML、畸形 JSON 和字段缺失得到格式错误；网络失败与业务失败能区分；取消无错误提示；localStorage 抛错时请求仍可使用会话标识。GET 查询重试策略和 POST 写入策略分别验证。

交付 API 错误约定、请求层实现及行为测试。先完成 A01，再让 A02 消费相同的错误和取消机制。

### A02 路线预览与演示入口 8工时

目标是“显示的路线确实对应最后一次选择的端点”。主改 pages/RoutePreviewPage.tsx 和 services/route.ts，并按约定整理 config/mockRoutes.ts。恢复真实错误和重试入口，取消请求不能触发演示回退。

端点变化时重新查询并取消旧请求；旧请求即使较晚返回，也不能覆盖新结果。演示必须由用户明确进入；按端点组合查找匹配路线，无匹配就显示无演示路线。不能把默认折线换个名称当作非默认路线。

| 场景 | 应观察到的结果 |
| --- | --- |
| 慢查询 A 后发快查询 B | 页面始终保留 B 的结果 |
| 网络失败后点击重试 | 再次查询相同端点 加载结束后有明确结果 |
| 非默认端点进入演示 | 只使用匹配数据 无匹配时明确提示 |
| 零条或单条候选路线 | 不崩溃 不补造第二条路线 |
| 评分不足或不可用 | 保留来源和状态 不把缺失值转成有效零分 |

后端尚未完成时用受控响应测试上述行为，并标注数据用途；最终与 B01、B02 的真实响应联调。建议先覆盖请求竞态，再改展示路径，避免只更新按钮文字却遗漏状态变化。

### 这一阶段的交付界限

A01 与 A02 完成后，应能说明每一次查询的端点、请求结果和来源。保存测试名称、失败复现与修复后的证据，并提供给 C 一份稳定的预览与地图输入样例。全局导航和通勤协议留到后续任务逐项接入。

## 五 页面编排与写入任务执行单

### A03 导航与能力状态 8工时

主改 App.tsx、pages/、types/index.ts，按需要新增 hooks。将底图、后端、路线来源、反馈来源和评分状态分别表达，再派生统一的能力判断。底图状态由 C 通知，路线和评分状态直接使用 B 返回的数据。

增加返回选择页、修改端点与重新规划。更换端点后清理旧比较结果、选中路线 ID 和旧通勤操作状态；页面刷新只恢复带版本的轻量配置，重新查询路线与趋势。浏览器返回与页面返回应采用同一导航规则。

验收场景：返回再规划不会携带旧路线；旧配置不可识别时回到安全默认；后端不可用时所有写入入口都受同一限制；底图离线但后端正常时，仍按能力表执行允许操作。与 C01 联调卡片、地图和按钮的一致性。

### A04 反馈刷新与通勤请求 10工时

这是 A 的重点联调任务。反馈保存成功后，只刷新最近一次有效地图视口；刷新失败显示“已提交但刷新失败”，重试只发查询。C 保留和管理反馈草稿，你负责调用 API 并将新增、重复、写入失败和刷新失败明确区分。

完成通勤时传递比较结果标识、路线 ID、用户感受和稳定操作 ID，由服务端快照提供评分与预计时长。客户端不再提交可覆盖服务端评分的字段；前后端需协调兼容顺序。

操作 ID 在开始一次通勤提交时创建，同次业务内容的网络重试复用该 ID；新通勤创建新 ID。按钮禁用只能防止部分重复操作，真正幂等由 D02 实现。超时可能发生在服务器已保存之后，不能据此新建 ID 再提交。

| 边界场景 | 验收结果 |
| --- | --- |
| 反馈保存成功 热力刷新失败 | 写入只有一次 可单独重试查询 |
| 通勤已保存但响应丢失 | 使用同一操作 ID 重试 趋势只增加一次 |
| 同一 ID 携带不同业务内容 | 显示明确冲突 不静默覆盖 |
| 快照过期 不存在或设备不符 | 提示重新规划或适当错误 不继续完成通勤 |
| 有效路线少于一分钟 | 使用秒数语义 可成功完成通勤 |
| 通勤成功 趋势刷新失败 | 保留成功结果 提供独立刷新警告 |

与 D01、D02 对接通勤，与 C02、D04 对接报告。开发可以使用契约样例并行，交付必须补齐真实接口证据。通勤恢复状态的保存与设备标识应协调，避免页面刷新后复用错误的身份或旧快照。
