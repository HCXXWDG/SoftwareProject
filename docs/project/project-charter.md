# 校园通勤情绪地图代码与功能优化项目启动书

版本：V1.0  
编制日期：2026 年 10 月 16 日  
实施对象：现有 SoftwareProject 项目  
文档用途：开发任务拆分、实施排序和技术验收

## 一 项目目标

本次优化以现有代码为基础，解决路线获取、离线回退、反馈提交、通勤记录和推荐展示中的一致性问题，补齐页面导航、状态恢复和可视化功能，并建立可维护的数据契约与回归测试。

预期交付一个能够稳定完成“选择起终点—获取路线—比较与选择—提交反馈—完成通勤—查看趋势—重新规划”流程的版本。每个页面都应准确表达加载、成功、空数据、失败及演示状态；用户操作失败后能够恢复，后台数据与界面展示保持一致。

本启动书仅安排代码与功能优化，不纳入赛事报名、市场推广、真实用户招募和线下应用组织。以下问题依据当前源码静态检查整理，尚未通过本轮运行测试逐项复现；实施时先建立基线，不将历史测试报告视为当前版本已经通过的证明。

## 二 当前技术基础

前端采用 React、TypeScript、Vite，地图层包含高德地图适配器和离线地图，测试使用 Vitest 与 Playwright。后端采用 Java 17、Spring Boot、JDBC 和 Flyway，提供 demo 与 postgres 两种运行方式，空间数据使用 PostGIS。项目已包含 PWA 和 Capacitor Android 相关配置。

已有能力包括起终点选择、路线预览与地图覆盖、情绪热力图、长按反馈、通勤完成记录和七日趋势。热力图请求已有防抖与取消机制；后端报告提交已有频率限制，JDBC 存储已有时间和空间范围内的重复检查；完成通勤已经区分写入失败与趋势刷新失败。这些能力应在优化中保留，并针对实际缺口补充行为。

## 四 第一阶段 核心正确性修复

### 4.1 路线提供与降级行为

将出行方式作为明确的业务参数，当前页面默认步行。对接适用的步行路线服务，按实现时的服务文档核对接口、权限和返回结构。真实服务只返回一条路线时允许单路线结果，不为凑足双路线而自动生成替代路径。

路线返回增加来源与状态信息，例如真实服务、预设演示路线、无可用路线及失败原因。前端模拟路线按起终点组合明确匹配；未配置组合显示无可用演示路线，不把默认路线替换成其他端点名称，也不使用直线插值冒充道路。

校验候选路线的坐标、折线有效性、距离和耗时。端点偏差检查需考虑道路吸附，使用可配置容差；空折线、非有限数值和非正耗时应得到可预测的错误结果。演示回退由明确策略控制，并向界面暴露原因。

涉及模块：AmapRouteProvider、RouteProvider、MockRouteProvider、RouteComparisonService、RoutePreviewPage、mockRoutes、前后端路线模型。

验收：默认及非默认端点均展示对应结果；单路线和无路线可正常渲染；外部服务失败不会变成未标识的模拟成功；异常候选不会进入评分除法和地图绘制。

### 4.2 统一来源状态与功能能力

分别表示底图状态、路线来源、反馈来源和后端可用性。离线底图不等于后端不可用，真实路线也不等于使用了真实反馈；不再依赖一个 isOfflineFallback 布尔值决定所有行为。

缺失评分使用明确的不可用状态或可空字段，不使用零分占位。零分只有在评分有效时才具有业务含义。预览页、路线卡片、图例、趋势及写入入口使用一致的状态判断；没有评分依据时隐藏少心累标签。

通过统一能力判断控制是否允许刷新热力图、提交报告和完成通勤。底图不可用而服务正常时可按支持范围继续操作；演示路线和演示反馈不得写入真实通勤统计。网络恢复后提供重新获取真实数据的入口。

涉及模块：App、types、MapSurface、RoutePreviewPage、RoutePanel、RouteLegend、TrendPanel、后端来源模型及仓储查询。

验收：离线预览进入地图后没有占位零分和无依据的标签；所有入口表现一致；拖动地图不会突破网络能力限制；真实统计查询明确排除模拟记录。

### 4.3 请求恢复与竞态控制

路线预览保留真实错误状态并提供重试，演示入口作为明确的可选操作。端点变化触发新查询；旧请求被取消或通过请求标识忽略，防止迟到响应覆盖新结果。路线服务方法支持传递取消信号。

API 层统一超时、主动取消、网络失败、业务失败和响应格式错误的表达。对关键响应进行运行时结构检查，避免将任意成功响应直接断言为有效业务对象。面向用户展示可操作的中文信息，调试日志保留诊断上下文。

查询可以受控重试；写入只有在幂等机制完成后才能安全重试。主动取消不显示为请求失败。localStorage 不可用时应使用受控的会话设备标识并说明保存限制，避免整个请求链因设备标识读取失败而中断。

涉及模块：RoutePreviewPage、services/api、services/route、热力图和趋势请求逻辑。

验收：超时后结束加载且能重试；快速更换端点不会展示旧路线；HTML 或畸形 JSON 响应不会导致页面崩溃；取消请求不触发错误提示。

### 4.4 反馈提交与地图刷新

提交失败时保留感受、原因和位置，显示错误并支持重试；成功后才关闭面板并播放成功动画。提交期间防止重复触发。沿用并验证后端已有的限频和重复判定，区分新增成功与重复反馈。

保存最近一次有效地图视口，提交成功后刷新该视口热力图。刷新失败应显示“已提交但地图刷新失败”，不能将写入成功改成提交失败，也不能自动再次写入。无数据变化的重复反馈无需假装新增热点。

涉及模块：MapSurface、FeedbackPanel、App、services/report、ReportService、报告控制器及仓储。

验收：强制失败后草稿仍在；重复点击不会连续写入；成功后热力图自动更新；保存成功但刷新失败时，只重试查询。

### 4.5 通勤记录与数据完整性

为一次通勤操作生成稳定的提交标识，后端以设备和提交标识建立唯一约束，demo 存储实现等价行为。同一操作重试返回已有结果，不能重复增加通勤次数；新的通勤使用新的标识。

路线比较结果返回查询或快照标识，完成通勤提交该标识与路线 ID，由服务端读取当时的路线评分和预计时长，校验设备归属及路线是否属于该结果。用户输入用于记录实际感受，不能覆盖服务端评分快照。

明确区分预计时长和实际时长。第一阶段保留预计秒数并正确命名；只有建立开始与结束记录后才提供实际时长。旧记录的 durationMinutes 来源未核实时标为历史口径，避免批量推断为实际耗时。短路线显示不足一分钟，不因取整产生无效提交。

涉及模块：App、commute service、CommuteController、CommuteService、路线历史仓储、CommuteRecordRepository、数据库迁移及趋势统计。

验收：相同提交标识重复发送只产生一条记录；篡改评分不能改变保存快照；无效或不属于当前设备的路线查询被拒绝；不足一分钟的有效路线能够记录；趋势刷新失败不会重复写入。

### 4.6 评分基础修正

将路线采样改为沿整条路径累计距离的固定间隔采样，或采用按路段长度加权的等价方案。处理重复点、零长度线段、空路径和异常间隔，保证分数不由上游折线顶点密度决定。

聚合与评分统一数据来源过滤。演示专用固定暴露值和数据充分程度只能进入演示结果。现有 confidence 含义是算法定义的样本参考量，应在界面解释为数据充分程度，避免显示成推荐正确率。

验收：在同一路径中插入共线点后，环境分和综合分在约定误差内不变；建议误差阈值不超过 0.1 分，由实现方案确定并固定为回归标准。缺少覆盖数据时返回数据不足状态，评分结果不存在 NaN 或无穷值。

## 五 第二阶段 核心功能与代码结构优化

### 5.1 导航与状态恢复

增加返回选择页、修改起终点和重新规划。保留当前端点和显示名称；改变端点后清理旧路线选择、旧比较结果及不再适用的通勤状态。页面刷新后恢复端点等轻量配置，路线与趋势重新查询。将持久化数据设置版本，无法识别的旧配置回到安全默认值。

验收：完整流程后可再次规划；新结果不会携带旧路线 ID；加载失败、空数据和未查询分别展示；浏览器返回操作与页面导航保持一致。

### 5.2 路线比较与推荐解释

路线卡片分别显示距离、预计耗时和环境感受指数。综合评分用于排序，并明确其包含时间因素。内部接口可以保留兼容字段，但应记录名称与含义的映射，避免修改数值语义却继续使用旧字段。

推荐结果增加结构化原因，如可推荐替代路线、没有替代路线、差异不足、绕行过长、数据不足、最快与舒适路线相同。页面根据原因展示对应说明；本次出发的推荐不使用“明天试”文案。

解释中包含可计算的耗时差异、环境差异和覆盖情况。若只有优势标签而没有足够分段依据，不生成具体路段结论。路线对比与地图选择同步，必要时定位到被选路线。

验收：每个推荐分支有匹配的文案；分数含义统一；仅一条路线时仍能使用；未知指数显示不可用而非零。

### 5.3 反馈交互与标签扩展

增加显式反馈按钮，进入选点模式后由用户确认位置，保留长按快捷操作。正向原因加入安静、树荫、开阔等有限选项，前端标签、后端枚举、数据库约束和测试数据同步更新；兼容现有负向标签。

改进弹层边缘定位、滚动、关闭操作和键盘焦点。地图拖动与面板点击不互相触发；操作提交后明确显示新增或重复结果。热力详情将英文枚举转换为中文，并展示有效数据时间、样本数量和来源状态。

验收：屏幕边缘打开面板不遮挡关键操作；鼠标、触摸和键盘均有可用流程；所有支持标签可保存并重新读取；未知标签有可理解的回退展示。

### 5.4 趋势与历史

七日趋势增加折线图和记录数量，保留可读取的明细。空日期不补零、不误连成连续趋势，横轴日期按统一时区生成。区分初次加载、无记录、加载失败和旧数据刷新失败；失败时可重试而不刷新整页。

复用已有路线历史接口增加最近查询入口，可恢复起终点后重新规划。历史评分明确对应当时的快照，不能直接当作当前环境状态。完成通勤后可以补充是否符合预期，作为单独评价字段保存。

验收：零记录、单日记录、跨日记录和断网场景均正确展示；历史路线重新使用时重新查询当前数据；新增通勤只增加一次统计。

### 5.5 前端职责整理

在关键缺陷修复后，按职责从 App 中抽离路线查询、热力图查询、通勤完成和趋势加载逻辑，可使用独立 hooks 或等价模块；App 负责页面编排。为路线请求和趋势请求分别维护状态，避免一个全局 error 覆盖其他功能。

统一情绪档位、中文标签、颜色及数值格式化。保留地图适配器、展示组件与 API 调用之间的边界；不为本次范围提前引入大型状态管理框架。代码结构调整不得改变已经修复的行为。

## 六 第三阶段 可选增强与性能优化

分时段推荐和个人偏好放在第二阶段之后。分时段查询必须统一作用于热力图与路线评分，缓存键包含时间范围；样本不足时说明回退范围。偏好设置需要实际影响评分，并展示参数变化带来的理由。优先选择一种能力完成，再决定是否扩展另一种。

先测量地图热点数量、路线采样点数、请求耗时和渲染耗时，再决定优化位置。当前评分按采样点逐个扫描格网，热点渲染也存在可避免的重复计算，可分别评估空间索引和投影函数稳定化。缓存需包含端点、出行方式、时间范围、来源、评分版本及偏好，反馈写入后应失效相关条目。

验证 PWA 更新及 Android API 地址配置，离线缓存只覆盖明确支持的资源，不缓存写入成功响应。是否发布 Android 安装包取决于功能和配置验证结果，不将原生扩展作为前两阶段的依赖。

## 七 接口与数据库变更原则

### 7.1 拟新增的数据概念

| 概念 | 作用 | 建议实现 |
| --- | --- | --- |
| 路线查询标识 | 关联候选路线与保存时的评分快照 | comparisonId 或等价查询 ID |
| 路线与反馈来源 | 区分真实、演示和不可用状态 | 分别设置来源字段，禁止由前端自行推断 |
| 评分状态 | 区分有效零分与无有效评分 | 有效、数据不足、不可用等状态配合可空分值 |
| 推荐原因 | 支持各页面一致解释 | 稳定原因代码及必要参数 |
| 通勤提交标识 | 避免同一操作重复计数 | 客户端操作 ID 与设备级唯一约束 |
| 统计口径 | 追溯计算与展示含义 | 评分版本、时间范围、有效样本及覆盖量 |

以上为设计建议，最终字段在实现前形成统一契约，并同步更新 TypeScript 类型、Java DTO、接口示例和测试样本。

### 7.2 迁移与兼容

数据库改动使用新增 Flyway 迁移，不改写已经执行的 V1 至 V3 脚本。新增标签时同步修改约束；新增来源、时长和幂等信息时设计历史数据兼容策略。无法恢复的历史来源或实际时长标记为未知，不通过填零制造完整性。

demo 和 postgres 模式应实现一致的来源、校验与重复提交语义。升级先验证全新数据库，再验证由现有版本迁移的数据库；涉及不可逆变更时先保留备份与恢复说明。

## 八 测试与技术验收

本轮按缺陷和功能建立行为测试，不追求机械增加测试数量。第一阶段先运行现有检查并记录失败，区分原有失败、环境限制和本轮引入的问题。

| 测试层次 | 重点覆盖 |
| --- | --- |
| 前端组件与请求 | 请求取消、迟到响应、错误重试、离线能力、缺失评分、草稿保留及状态重置 |
| 后端服务 | 来源隔离、路线校验、评分采样、原因分支、快照归属和重复提交 |

实施时使用仓库现有命令：前端 npm run build、npm test、npm run test:e2e；后端 mvnw.cmd verify；前后端联调使用 npm run test:e2e:integration。数据库集成依赖 Docker 或等价测试环境，真实地图连接验证需要相应服务配置。环境缺失导致跳过的检查必须单独列出，不计为通过。

发布前至少通过以下场景：

1. 默认和非默认端点均获取或明确无法获取对应路线。
2. 相同端点、无候选、单候选、异常时长和空折线得到明确处理。
3. API 失败后能够重试；选择演示模式后全页面来源标识一致。
4. 离线结果不出现占位零分和无依据的舒适标签，不进入真实统计。
5. 连续查询时只展示最后一次选择的结果。
6. 反馈失败保留草稿，成功后刷新当前视口；查询失败不重复写入。
7. 同一次通勤重复发送和并发发送仅增加一条记录。
8. 完成通勤的评分取自服务端快照，预计时长与实际时长不混淆。
9. 模拟记录不参与真实模式统计；几何等价路线评分保持稳定。
10. 返回、重新规划、趋势重试和移动端面板操作均无阻断问题。

## 十 开发分工与交付要求

三人和四人的具体任务包、文件责任、前置依赖、工作量及建议执行节奏，见配套的[代码与功能优化任务分工书](task-assignment.md)。任务分工书是本启动书的执行拆分，采用相同的功能范围和验收要求。

前端负责页面状态、请求恢复、交互和可视化；后端负责路线提供、来源隔离、评分、快照、幂等及迁移；质量验证负责缺陷复现、端到端场景、数据库升级和移动端检查。各角色可以兼任，关键接口和数据迁移由另一成员复核。

每项任务需包含问题表现、涉及文件、实现方案、验收场景和完成记录。每次提交围绕一个可验证的行为，功能修复与大规模重构分步进行。同步更新代码注释和测试，避免出现注释要求重试而实现自动回退的情况。

交付物包括优化后的前后端代码、数据库迁移、接口与状态说明、必要配置示例、测试结果、已知限制及启动操作说明。第一阶段交付不能依赖尚未实现的个人偏好、分时段统计或额外平台功能。

完成标准：所选阶段范围内的缺陷得到复现和修复，相关回归通过，接口和数据库升级可执行，页面展示与后台状态一致，运行说明能够指导重新启动项目。本启动书本身不代表上述改动已经实施。
