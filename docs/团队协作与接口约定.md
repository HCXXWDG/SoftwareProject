# 城市通勤情绪地图：A/B/C 团队协作与接口约定

版本：v1.0  
冻结日期：2026-06-10  
适用分支：`develop` 及所有功能分支

## 1. 角色与代码边界

### 成员 A：项目管理与基础前端

主要维护：

```text
frontend/src/app/
frontend/src/pages/
frontend/src/components/
frontend/src/services/
docs/项目管理/
```

负责：

- React 项目初始化、路由、页面框架和全局样式。
- 匿名设备 ID 的生成、持久化和请求头注入。
- API Client、加载状态、错误提示和通勤趋势图。
- 产品原型、需求文档、迭代记录和答辩材料。

不直接修改 C 的地图渲染、地图事件和路线动画实现。需要地图能力时，通过本文件约定的组件接口传递数据。

### 成员 B：后端与空间数据

主要维护：

```text
backend/
infra/
data/seed/
```

负责：

- Spring Boot API、PostGIS、Flyway 和模拟数据。
- 情绪衰减聚合、网格生成、空间检索和路线评分。
- 高德 Web Service 调用、密钥保护和后端降级逻辑。
- OpenAPI、后端单元测试和数据库集成测试。

不要求前端理解 PostGIS 或路线评分细节。B 必须保持接口返回结构稳定，并提供可用的 `demo` Profile。

### 成员 C：地图交互与质量保证

主要维护：

```text
frontend/src/features/map/
frontend/src/features/routes/
frontend/e2e/
.github/workflows/
docs/测试/
```

负责：

- 高德 JS API 2.0 加载及无 Key 演示地图。
- 热力图绘制、250ms 缩放过渡和图层刷新。
- 长按 600ms、emoji 喷泉、路段情绪选择。
- 双路线绘制、路线切换、动画和图例。
- Vitest、Playwright、CI、兼容性测试和演示降级方案。

C 不直接在地图组件内调用后端。地图组件通过回调把用户操作交给 A，A 的 API Client 完成请求并把结果重新传入地图组件。

## 2. A 与 C 的前端组件契约

A 负责页面状态和网络请求，C 只负责地图及路线的可视化和交互。

```ts
export type GeoPoint = {
  longitude: number;
  latitude: number;
};

export type EmotionTag = "NOISE" | "CROWD" | "SUN" | "ODOR" | "OTHER";

export type HeatmapCell = {
  cellId: string;
  center: GeoPoint;
  score: number;
  confidence: number;
  count: number;
  dominantTag: EmotionTag;
};

export type ScoredRoute = {
  id: string;
  label: string;
  distanceMeters: number;
  durationSeconds: number;
  stressExposure: number;
  stressScore: number;
  confidence: number;
  fastest: boolean;
  leastStressful: boolean;
  polyline: GeoPoint[];
};

export type MapFeedbackDraft = {
  location: GeoPoint;
  stressLevel: 0 | 25 | 50 | 75 | 100;
  tag: EmotionTag;
};

export type CommuteMapProps = {
  heatmapCells: HeatmapCell[];
  routes: ScoredRoute[];
  selectedRouteId?: string;
  loading: boolean;
  onFeedbackSubmit: (draft: MapFeedbackDraft) => Promise<void>;
  onRouteSelect: (routeId: string) => void;
  onViewportChange: (bbox: string, zoom: number) => void;
};
```

约定：

- C 的组件不得保存业务真相；`routes`、`heatmapCells` 和 `selectedRouteId` 均由 A 传入。
- 地图缩放或移动结束后，C 调用 `onViewportChange`，A 做 300ms 防抖后请求热力图。
- 用户完成 emoji 选择后，C 调用 `onFeedbackSubmit`；Promise 完成前禁用重复提交。
- A 负责成功、重复、限流和网络失败提示；C 负责喷泉动画及地图上的视觉反馈。
- C 需要新增 Props 时先在 PR 描述中给出类型和使用场景，由 A 确认后修改。

## 3. B 与 A/C 的 API 契约

所有前端请求使用：

```http
X-Device-Id: <浏览器生成的匿名ID>
Content-Type: application/json
```

坐标统一使用 GCJ-02，经纬度顺序固定为：

```json
{
  "longitude": 116.4,
  "latitude": 39.9
}
```

### 提交情绪反馈

```http
POST /api/v1/reports
```

```json
{
  "location": {
    "longitude": 116.4,
    "latitude": 39.9
  },
  "stressLevel": 75,
  "tag": "CROWD",
  "reportedAt": "2026-06-10T08:30:00Z"
}
```

状态码：

- `201`：创建成功。
- `409`：五分钟内在附近重复提交。
- `429`：一分钟内提交次数超限。
- `400`：字段或坐标不合法。

### 获取热力图

```http
GET /api/v1/heatmap?bbox=116.39,39.90,116.41,39.92&zoom=16&hours=168
```

响应：

```json
[
  {
    "cellId": "16:129333:44333",
    "center": {
      "longitude": 116.4,
      "latitude": 39.91
    },
    "score": 68.2,
    "confidence": 0.72,
    "count": 18,
    "dominantTag": "NOISE"
  }
]
```

C 的渲染约定：

- `score` 决定蓝到红的颜色。
- `confidence` 决定透明度，最低可视透明度为 0.18。
- `count` 和 `dominantTag` 用于点击后的详情浮层。

### 对比候选路线

```http
POST /api/v1/routes/compare
```

```json
{
  "origin": {
    "longitude": 116.392,
    "latitude": 39.905
  },
  "destination": {
    "longitude": 116.405,
    "latitude": 39.912
  }
}
```

响应：

```json
{
  "routes": [
    {
      "id": "route-fast",
      "label": "最快路线 A",
      "distanceMeters": 2100,
      "durationSeconds": 720,
      "stressExposure": 67.2,
      "stressScore": 50.4,
      "confidence": 0.68,
      "fastest": true,
      "leastStressful": false,
      "polyline": [
        {"longitude": 116.392, "latitude": 39.905}
      ]
    }
  ],
  "fastestRouteId": "route-fast",
  "leastStressfulRouteId": "route-calm",
  "recommendation": "明天试少心累路线 B。",
  "recommendAlternative": true
}
```

C 只绘制后端返回的折线，不在前端重新计算路线分数。

### 完成通勤与趋势

```http
POST /api/v1/commutes/complete
GET /api/v1/commutes/trends?days=7&timezone=Asia/Shanghai
```

这两个接口由 A 集成。C 只需要向 A 返回用户最终选择的 `routeId`。

## 4. 联调与交付顺序

1. A 先提交 React 空壳、共享类型和 Mock API Client。
2. C 基于固定 Mock 数据完成地图、长按反馈及双路线动画。
3. B 保证 `demo` Profile 启动后四组 API 可调用，并提交 OpenAPI。
4. A 将 Mock API Client 切换为真实 API。
5. C 使用真实热力图和路线响应完成视觉校准。
6. 三人共同跑通“热力图→反馈→路线对比→完成通勤→趋势建议”。

每个阶段完成后都必须合并到 `develop`，后续阶段不得长期依赖其他成员未推送的本地代码。

## 5. Git 协作规则

- A：`feature/frontend-*`、`docs/*`
- B：`feature/backend-*`、`feature/postgis-*`
- C：`feature/map-*`、`feature/route-animation`、`test/*`、`ci/*`

每次开始任务：

```powershell
git switch develop
git pull origin develop
git switch -c feature/具体任务
```

每个 PR 必须：

- 只完成一个 Issue。
- 合并目标为 `develop`。
- 至少由一名非作者评审。
- 写明接口是否变化、测试结果和截图。
- CI 通过后才能合并。

禁止：

- 直接推送 `main` 或 `develop`。
- 在聊天中口头修改接口而不更新本文件/OpenAPI。
- 提交 `.env`、高德 Key、数据库密码。
- 用强制推送覆盖其他成员提交。

## 6. 接口变更流程

任何人需要修改字段、状态码、组件 Props 或坐标规则时：

1. 创建 `[Contract]` Issue，写清旧结构、新结构及修改原因。
2. A、B、C 三方在 Issue 中确认影响。
3. B 先更新 OpenAPI；A 更新共享 TypeScript 类型；C 更新地图适配。
4. 同一个迭代内完成迁移，不允许 `develop` 长期存在不兼容接口。
5. 破坏性修改提升接口版本，例如从 `/api/v1` 迁移到 `/api/v2`。

未走上述流程的接口改动，评审人应拒绝合并。

## 7. 三方验收标准

- A 验收 C：页面可控制地图状态；错误、加载和空数据状态清楚。
- B 验收 C：前端没有复制路线评分逻辑；坐标顺序和坐标系正确。
- C 验收 A：地图容器尺寸稳定；Props 更新不会导致地图重复初始化。
- C 验收 B：热力图字段完整；路线折线至少两个点；无 Key 时有模拟降级。
- 共同验收：Chrome 和 Edge 最新版可完成核心链路，课堂网络断开后仍能演示。
