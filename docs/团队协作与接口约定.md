### 提交情绪反馈

```http
POST /api/v1/reports
```

```json
{
  "location": {
    "longitude": 116.4,
    "latitude": 39.9
  },
  "stressLevel": 75,
  "tag": "CROWD",
  "reportedAt": "2026-06-10T08:30:00Z"
}
```

`tag` 取值（与前端 `EmotionTag` 联合类型、数据库 CHECK 约束三处一致，由 D03 统一）：

| 枚举名 | 中文 | 类型 |
| --- | --- | --- |
| `NOISE` | 噪音 | 负面成因 |
| `CROWD` | 拥挤 | 负面成因 |
| `SUN` | 暴晒 | 负面成因 |
| `ODOR` | 异味 | 负面成因 |
| `QUIET` | 安静 | 正向原因（C03 新增） |
| `SHADE` | 树荫 | 正向原因（C03 新增） |
| `OPEN` | 开阔 | 正向原因（C03 新增） |
| `OTHER` | 其他 | 兜底 |

未在表内的取值一律返回 `400 invalid_request`，后端不做猜测映射。中文名与 emoji 由前端负责展示，后端只存枚举名。

响应（D04 起成功与重复统一用同一套字段，前端只读 `code` / `counted` 即可分支）：

```json
{
  "status": "created",
  "code": "report_created",
  "counted": true,
  "message": "情绪反馈已加入热力图。"
}
```

| HTTP | `status` | `code` | `counted` | 含义 |
| --- | --- | --- | --- | --- |
| `201` | `created` | `report_created` | `true` | 新增成功，计入反馈数 |
| `200` | `duplicate` | `report_duplicate` | `false` | 同设备 5 分钟内、25 米内重复提交，已记录但不重复计数 |
| `429` | — | `rate_limited` | — | 同设备一分钟内超过 10 次 |
| `400` | — | `invalid_request` | — | 压力值/标签/坐标/时间戳不合法，或缺 `X-Device-Id` |

4xx 响应体为统一错误信封 `{timestamp, status(数字), code, message}`。

**重复提交从 `409` 改为 `200`**：前端 `services/api.ts` 对所有非 2xx 一律抛异常，`409` 会让 C02 已写好的 `result.status === "duplicate"` 分支永远走不到，重复提示成了死代码。重复提交不是错误——请求被正确理解并已有记录，只是不再计数，因此用 `200 + counted:false` 表达。C 的现有判断无需修改即可生效；A 若要区分错误与重复，请读 `code` 而不是 HTTP 状态码。

去重口径由 `ReportDeduplication` 单点定义（窗口 5 分钟、半径 25 米、仅同设备之间），demo 内存实现直接调用它，postgres 实现在 SQL 中使用同源常量，两种模式不会出现相反行为。并发下同一设备的“查重 + 写入”已串行化：内存用写锁，postgres 用事务级咨询锁 `pg_advisory_xact_lock(hashtext(device_hash))`，避免两个并发请求都查不到重复而各写一条。

### 数据来源口径（simulated 隔离）

`emotion_report.simulated` 标记该条记录是演示种子（`true`）还是真实用户反馈（`false`）。仓储层用 `ReportScope` 表达查询口径：

| 口径 | 含义 | 使用场景 |
| --- | --- | --- |
| `REAL_ONLY` | 只取真实反馈 | 任何真实统计、验收取数、报告分析 |
| `SIMULATED_ONLY` | 只取演示数据 | 演示自检、清理演示数据 |
| `ALL` | 不区分来源 | 仅演示模式展示（默认 profile 下所有数据都是模拟数据） |

接口签名：`findWithin(bounds, since, scope)`；两参重载 `findWithin(bounds, since)` 固定为 `ALL`，仅为兼容既有调用保留，新代码必须显式传口径。内存与 JDBC 实现的筛选规则一致（时间下界闭区间、边界框闭区间、按 `simulated` 过滤），JDBC 侧对 `REAL_ONLY` 使用 V5 建立的部分索引。

**B 需要跟进**：`HeatmapService`（第 44 行）与路线采样目前走两参重载，等价于 `ALL`。真实部署统计需改为按配置或请求参数传入 `REAL_ONLY`，否则演示种子会计入热力分。此项属 B05 范围，D 只提供口径能力，未改 B 的业务服务。

#### 趋势口径（D05，A/C 必须按此渲染）

四条口径由 `TrendService` 单点定义，前端不要重复实现：

| 口径 | 规则 | 前端注意 |
| --- | --- | --- |
| 日期与时区 | 窗口是"请求时区下的自然日"，含今天共 `days` 天；查询下界就是首日 00:00 | `points` 恒为 `days` 个、日期严格升序、无缺口 |
| 空日期 | 当天没有记录时 `averageStress` 为 `null`、`commuteCount` 为 0 | **不补零**，折线在此断开，不要连成 0 |
| 预计时长 | 只对带 `estimatedSeconds` 的记录求均值，样本数见 `estimatedSampleCount` | 样本数为 0 时不要展示时长，更不要显示 0 秒 |
| 来源筛选 | 写入侧**不再拒绝**演示快照（D07）：`routeSource=DEMO` 照常落库，但读侧不计入任何统计；`UNKNOWN` 计入但单独计数 | 需要"仅真实数据"时看 `unknownSourceCommutes`/`excludedDemoCommutes` |
| 评分可空 | 没有可验证评分时 `selectedScore`/`fastestScore`/`confidence` 为 `null`（V6 起数据库列也可空），**不补 0** | 键整个不出现，判定写 `value == null`；不要把缺失当 0 分渲染 |

`totalCommutes` = 各日 `commuteCount` 之和 = 窗口内被计入的通勤次数。**同一次通勤的重复写入不会增加这个数**：写侧幂等（D02 的 `operationId`）先挡一层，读侧 `CommuteRecordDeduplication` 再折叠一层（覆盖没有 `operationId` 的历史数据），折叠条数在 `deduplicatedCommutes` 里可见。

响应字段（前四个是既有契约，其余为 D05 追加，只增不改，旧前端忽略即可）：

```json
{
  "points": [
    {
      "date": "2026-10-19",
      "averageStress": 50.0,
      "commuteCount": 1,
      "averageEstimatedSeconds": 39722.0,
      "estimatedSampleCount": 1
    },
    { "date": "2026-10-20", "commuteCount": 0, "estimatedSampleCount": 0 }
  ],
  "recommendation": "明天试 少心累路线 B，预计更从容。",
  "totalCommutes": 6,
  "summary": {
    "averageStress": 45.83,
    "stressDelta": -25.0,
    "direction": "improving",
    "sampleSufficient": true
  },
  "days": 7,
  "timezone": "Asia/Shanghai",
  "unknownSourceCommutes": 6,
  "excludedDemoCommutes": 0,
  "deduplicatedCommutes": 0,
  "outOfWindowCommutes": 0
}
```

**注意**：后端 Jackson 配置为 `default-property-inclusion: non_null`，值为 `null` 的字段在 JSON 里**整个键都不出现**（上面第二个点就是空日期的真实形状）。前端判定必须写 `value == null`（同时覆盖 `undefined`），不要用 `"key" in obj`。

`direction` 取值 `improving`（降幅 ≥ 5）/ `worsening`（升幅 ≥ 5）/ `stable` / `unknown`（不足 2 条）；`sampleSufficient` 为 `true` 才建议展示趋势结论。`outOfWindowCommutes` 统计完成时间落在窗口自然日之外（含前端提交的未来时间）的记录，它们不进任何日桶，以免 `points` 失去升序。

#### 写入放行与评分可空口径（D07，A 必须按此处理 201/4xx）

D02~D06 期间 `POST /commutes/complete` 会在两种情况下**拒绝写入**：快照来源是 `DEMO`（422 `demo_result_not_allowed`），以及快照没有可验证评分（400）。B 的 #67 让"没有可验证评分"变成一种**正常状态**（`ScoringStatus.INSUFFICIENT_DATA` / `UNAVAILABLE`，典型场景是真实用户的第一次通勤：路线服务可用，但沿途还没有任何真实反馈）。如果继续沿用拒绝口径，真实用户的第一条记录会直接失败。D07 起改为：

| 情况 | 旧口径 | 新口径（D07） |
| --- | --- | --- |
| 快照 `routeSource=DEMO` | 422 `demo_result_not_allowed` | **201 写入**，`routeSource` 原样落库，读侧（trends/history）排除，计入 `excludedDemoCommutes` |
| 快照无可验证评分 | 400 拒绝 | **201 写入**，三个评分字段留 `null`，次数照常计入 trends |
| 正常真实通勤（`REAL` + `VALID` 评分） | 201 | 201（不变，三个评分字段照常写入） |

写入侧只做两件判断：幂等（`operationId` 重复 → 200 `duplicate`）和快照归属（快照不属于本设备 → 404 `snapshot_not_found`）。**评分有没有不再影响能不能写**，只影响写进去的评分字段是否为 `null`；来源是否演示也不再影响能不能写，只影响读侧是否统计。

前端注意：

- `demo_result_not_allowed` 已不再由后端抛出，A 可以移除对应的 422 分支（保留也无害，属于死代码）。
- 完成通勤返回体里 `selectedScore`/`fastestScore`/`confidence` **可能整个键都不存在**。展示"本次通勤压力评分"时必须判空，缺失时显示"暂无评分，完成几次通勤后会出现"，**不要显示 0 分**（0 分是合法取值，含义是"完全没压力"）。
- 数据库层面 `commute_record.selected_score` / `fastest_score` / `confidence` 从 V6 起可空，并补了取值范围 CHECK（`0~100` / `0~100` / `0~1`）。V6 只放宽约束，不改写 V1~V5，已有行全部有值，升级无需数据修复。

#### 历史明细口径（D05）

`GET /api/v1/commutes/history` 返回**数组**，按 `completedAt` 倒序，最多 `limit`（1–100，默认 20）条，回溯 `days`（1–90，默认 30）个自然日。它与 `trends` 共用同一时区、同一自然日窗口和同一去重口径，因此"趋势说 6 次、历史列出 6 条"。`routeSource=DEMO` 的记录不出现在历史里。

旧数据兼容靠两个显式标记，前端不必猜测：

```json
[
  {
    "commuteId": "81f936c1-e97e-4e84-aa29-2c4adaba73b0",
    "completedAt": "2026-10-18T15:21:30.203819Z",
    "completedDate": "2026-10-18",
    "timezone": "Asia/Shanghai",
    "routeId": "route-fast",
    "routeLabel": "最快路线 A",
    "routeSource": "UNKNOWN",
    "endStressLevel": 25,
    "durationMinutes": 24,
    "selectedScore": 62.0,
    "fastestScore": 62.0,
    "alternativeLabel": "少心累路线 B",
    "alternativeScore": 43.0,
    "alternativeDurationRatio": 1.12,
    "confidence": 0.72,
    "legacyRecord": true,
    "missingFields": ["operationId", "snapshotId", "estimatedSeconds"]
  }
]
```

- `legacyRecord=true` 表示这是缺新字段的旧记录，应显示"旧记录"角标；`missingFields` 列出具体缺哪几项（取值只有 `operationId`/`snapshotId`/`estimatedSeconds`）。
- `routeSource="UNKNOWN"` **不等于**旧记录：它表示"快照没有声明来源"。B04（#67）之后 `CommuteService.resolveRouteSource` 只做归类、不再拒绝写入，来源直接取快照里 B 声明的 `routeSource`，取不到才是 `UNKNOWN`；B04 之前写入的历史记录也一律是 `UNKNOWN`。两种情况前端都按来源角标处理，不进 `missingFields`。
- `selectedScore`/`fastestScore`/`confidence` 缺失（键不存在）表示这次通勤**没有可验证评分**，不是 0 分，也不是旧记录；旧记录只看 `legacyRecord`/`missingFields`。
- `completedDate`/`timezone` 由后端按请求时区算好，前端**不要**再用本地时区二次换算，否则跨日记录会归错天。
- 时长展示优先用 `estimatedSeconds`（服务端权威）；它缺失时才退回 `durationMinutes`（兼容字段，不是实测时长）。

## 5. Git 协作规则

- A：`feature/frontend-*`、`docs/*`
- B：`feature/backend-*`、`feature/postgis-*`
- C：`feature/map-*`、`feature/route-animation`、`test/*`、`ci/*`

每次开始任务：

```powershell
git switch develop
git pull origin develop
git switch -c feature/具体任务
```

每个 PR 必须：

- 只完成一个 Issue。
- 合并目标为 `develop`。
- 至少由一名非作者评审。
- 写明接口是否变化、测试结果和截图。
- CI 通过后才能合并。

禁止：

- 直接推送 `main` 或 `develop`。
- 在聊天中口头修改接口而不更新本文件/OpenAPI。
- 提交 `.env`、高德 Key、数据库密码。
- 用强制推送覆盖其他成员提交。

## 6. 接口变更流程

任何人需要修改字段、状态码、组件 Props 或坐标规则时：

1. 创建 `[Contract]` Issue，写清旧结构、新结构及修改原因。
2. A、B、C 三方在 Issue 中确认影响。
3. B 先更新 OpenAPI；A 更新共享 TypeScript 类型；C 更新地图适配。
4. 同一个迭代内完成迁移，不允许 `develop` 长期存在不兼容接口。
5. 破坏性修改提升接口版本，例如从 `/api/v1` 迁移到 `/api/v2`。

未走上述流程的接口改动，评审人应拒绝合并。

## 7. 三方验收标准

- A 验收 C：页面可控制地图状态；错误、加载和空数据状态清楚。
- B 验收 C：前端没有复制路线评分逻辑；坐标顺序和坐标系正确。
- C 验收 A：地图容器尺寸稳定；Props 更新不会导致地图重复初始化。
- C 验收 B：热力图字段完整；路线折线至少两个点；无 Key 时有模拟降级。
- 共同验收：Chrome 和 Edge 最新版可完成核心链路，课堂网络断开后仍能演示。
